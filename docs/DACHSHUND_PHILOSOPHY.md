# Dachshund Philosophy

Dachshund starts from a simple shift: treat language-model behavior as software, not
as loose prompt text. You do not need to know another language or framework to
use Dachshund. The system is taught from Elixir first: explicit data, behaviours,
processes, immutable program structs, tests, and production gates.

Dachshund is the project name for declarative self-improving programs in
Elixir.

## The System In One Sentence

Dachshund turns language-model work into declared, callable, measurable, improvable
Elixir programs.

## The Pieces

- Signatures are data: `%Dachshund.Signature{}` declares inputs, outputs,
  instructions, and constraints. Use `Dachshund.signature/2` at the public edge.
- Programs are structs: Predict, ChainOfThought, ReActV2, RLM, and related
  modules hold configuration, demos, adapters, and LMs.
- Boundaries are behaviours: LM, adapter, retrieval, and HTTP clients are
  explicit seams for tests and production clients.
- Optimization is metric-driven: optimizers compile better programs from
  examples, dev sets, and scores.
- The BEAM shapes the design: immutable structs, supervised cache state,
  injectable transports, safe sandboxing, and deterministic tests.

## Why This Is Not Prompt Engineering

A prompt is a string. A Dachshund program is an object with a contract, runtime
configuration, traces, examples, metrics, and optimization history.

The prompt is generated by an adapter. It is not the whole system.

```elixir
program = Dachshund.predict("question -> answer", lm: lm)
{:ok, pred} = Dachshund.call(program, %{question: "Capital of France?"})
Dachshund.get(pred, :answer)
```

## Core Concepts

### Signature

A signature names the task boundary. Inputs and outputs are contract fields,
not prose convention.

```elixir
signature =
  Dachshund.signature(%{
    inputs: [:text],
    outputs: [
      %{name: :sentiment, type: :string, constraints: %{enum: ["positive", "negative"]}},
      %{name: :confidence, type: :number, constraints: %{min: 0.0, max: 1.0}}
    ]
  })
```

### Module

A module is a callable program shape. The simplest one is `Predict`; others add
reasoning, tools, code execution, comparison, refinement, parallelism, or
recursive exploration.

### Adapter

An adapter translates signatures and examples into LM messages, and translates
raw model output back into `Dachshund.Prediction`.

### Example

An example is a row of data plus optional input-key metadata. Optimizers use
examples as train/dev material.

### Metric

A metric turns `(example, prediction)` into a score. The score is the language
that optimizers understand.

### Optimizer

Optimizers compile a better program by searching instructions, demos, candidate
programs, or arbitrary text artifacts.

## Concept Map

| Concept | Elixir shape |
| --- | --- |
| Public facade | `Dachshund` |
| Signature | `Dachshund.signature/2`, `%Dachshund.Signature{}` |
| Program | `Dachshund.predict/2`, `chain_of_thought/2`, `react_v2/3`, `rlm/2` |
| Call boundary | `Dachshund.call/2` |
| Example | `Dachshund.example/1`, `%Dachshund.Example{}` |
| Prediction | `Dachshund.prediction/1`, `%Dachshund.Prediction{}` |
| Metric/evaluation | `Dachshund.Metrics`, `Dachshund.Evaluate` |
| Optimizers | `Dachshund.Optimizer.*`, `Dachshund.Optimize.*` |
| Tools/agents/MCP | `Dachshund.Tool`, `Dachshund.Agent`, `Dachshund.MCP` |

## Production Principle

The codebase should be judged by gates, not vibes:

```sh
mix production.check
mix v2.check
LIVE_PROVIDER=1 mix test --include live test/live_provider_test.exs
```

The first two are deterministic. The live gate is opt-in because provider
credentials and account state are operational concerns.
